# Host checks (barangay PC)

Nothing in this file has been run yet. It is the checklist for the first time the system is installed on the real server computer. Each check says what to do, what a pass looks like, and where to write the result. **A check that was not run is not a pass**; record failures too.

Use synthetic data only until the real-data gate (D-40) is passed. Run PowerShell from the repository folder unless a step says otherwise.

## A. Backup, wipe and restore (D-35)

Why: a backup that was never restored is not a recovery plan.

1. Start the app: `docker compose -f compose.yml up -d`. Sign in as the System Administrator. Add one test resident ("Test Resident One").
2. Open **Backup and Restore** and press **Back up now**. Pass: a row appears with status **Verified**, and a `mayondon-db-….dump` file exists in `backups\` on the host.
3. Press **Verify file** on that row, then **Download copy**. Pass: both succeed and the downloaded file is the same size as the one in `backups\`.
4. Make a second change that the backup does not contain: add "Test Resident Two".
5. Select the backup, press **Prepare Restore**, type `RESTORE`, press **Check and Show Command**. Pass: the page shows `.\scripts\restore-db.ps1 -BackupFile .\backups\…` and nothing has changed yet (Resident Two is still there).
6. Run that command in PowerShell and type `RESTORE` when asked. Pass: the script ends without an error and restarts the backend.
7. Sign in again. Pass: Resident One is there, Resident Two is gone, issuance history and the Activity Log open normally. (The backup history shows only what the backup knew; that is expected.)
8. Make a new backup after the restore and confirm it is **Verified**.

### Scheduled backup

1. Register the task: `.\scripts\register-backup-task.ps1 -Time 17:00` (add `-CopyTo "E:\MayondonBackups"` when the external drive is plugged in; use the real drive letter).
2. Start it now: `Start-ScheduledTask -TaskName "Mayondon Database Backup"`. Wait a minute.
3. Pass: `backups\last-run.json` says `"ok": true`, a new row with type **Scheduled** appears on the page, and (with `-CopyTo`) the file is also on the external drive.
4. Leave it for two days. Pass: one new scheduled backup per day, and no more than 14 files in `backups\` (and in the copy folder).
5. Negative test: stop Docker Desktop, start the task again. Pass: `last-run.json` says `"ok": false` with a readable message, no crash.
6. Decide with the barangay: the task runs only while the Windows user is signed in (default). `-RunWhetherLoggedOn` also runs it signed out but only works if Docker Desktop is running then; test it before relying on it.
7. Remove it if needed: `.\scripts\register-backup-task.ps1 -Unregister`.

Open client answers (D-35): the real schedule, which drive and who keeps it, how many copies, and whether backup files must be protected (D-33). The defaults are daily, 14 copies, `backups\`.

## B. Docker Desktop starts at Windows sign-in (D-34)

1. Check Docker Desktop's licence terms for the client's use.
2. Restart Windows and sign in. Do not open Docker Desktop yourself.
3. Pass: Docker Desktop starts by itself, the containers come up (`restart: unless-stopped`), `Invoke-WebRequest http://localhost:8000/api/v1/utils/health-check/` returns 200 and the login page loads. Write down the time from sign-in to ready.
4. Restart again and do **not** sign in. Record whether the app is reachable from another PC. Availability before sign-in is not promised until this passes.

## C. Access from a second PC (D-31, D-32)

1. On the host, find its IPv4 address (`ipconfig`).
2. On another PC on the same network open `http://<host-IPv4>:8000`. Pass: the login page loads; sign in as staff, open Records, Issuances and the Dashboard.
3. Put the host to sleep, wake it, reload from the second PC. Then restart the host and try again. Record what happens.
4. Ask the network administrator to reserve the host's IP address in the router.

## D. Printer sharing (D-32)

1. Share the printer from the host, or install it on each workstation.
2. Print a test page from the second PC. Pass: it prints. (Aligning real documents is printing step 17, later.)

## E. Firewall (D-31, D-32)

1. Windows Defender Firewall stays **on**. Allow inbound TCP 8000 on the **Private** profile only.
2. From the second PC: `Test-NetConnection <host-IPv4> -Port 8000` must succeed and `Test-NetConnection <host-IPv4> -Port 5432` must **fail** (PostgreSQL is bound to `127.0.0.1` in `compose.yml`).

## F. First set-up on a new installation (administrator)

A fresh database is empty. Do these once, signed in as the System Administrator, before staff start work.

1. **Streets.** Staff cannot add streets (only the administrator can). Open the resident form and check the street list; if it says no streets have been added, add every street and purok of the barangay first. Without them residents cannot be saved with an address and the masterlist import rejects every street.
2. **Staff accounts.** Add User creates the account with the default password and a forced change at first sign-in. Create each account with the person present, hand over the default password in person and let them change it at once. The account is active by default; untick "Is active?" only to hold an account back.
3. **Locked accounts.** After repeated wrong passwords an account locks for a while. The Users table shows "Locked until"; Edit User has "Unlock this account", which leaves the password alone.
4. **Camera for photos.** The browser allows the camera only on `localhost` or over HTTPS. On the plain-HTTP office network a second PC cannot take photos with the camera (uploading a file still works); take Barangay ID photos on the host PC until HTTPS is set up. Record what you find.
5. **Change every default secret** in `.env` before real data goes in (`FIRST_SUPERUSER_PASSWORD`, `SECRET_KEY`, the database password) and leave `FASTAPI_ENV` and `ENABLE_DEV_ROUTES` blank.
6. **After every update, restart the backend.** If a button answers "Method Not Allowed" or "No API route POST /api/...", the running backend is older than the screens (for example Backup and Restore without the create-backup route). Rebuild and restart it (`docker compose build backend && docker compose up -d`) and try again.
7. **The database updates itself.** Every start of the backend brings the database up to date. When the database is behind and holds data, it first saves a safety copy named `mayondon-premigrate-<time>-from-<revision>.dump` in `backups\` (these files are not listed on the Backup and Restore page and are never deleted automatically; remove old ones by hand when you are sure they are not needed). Check with `docker compose logs backend --tail 30`: you should see `[migrate] Database is up to date` or `[migrate] Database is now up to date`. If the backend keeps restarting, the same log says why (`[migrate] STOP: ...`): a database newer than the program (an old image was started), a failed safety copy (the database was not changed), or a failed migration (rolled back). Nothing is changed in any of those cases. To restore a safety copy use the normal restore procedure in section A. `MIGRATE_ON_START=false` and `PRE_MIGRATION_BACKUP=false` in `.env` turn the steps off; do not use them without a reason.

## G. Protecting the data (step 15)

Done so far (patches 51 to 57 and 62). More items are added here as each patch lands.

1. **Never start the real system with the development files.** On the server computer add `COMPOSE_FILE=compose.yml` to `.env` (the line is in `.env.example`, commented). Then even a plain `docker compose up -d` ignores `compose.override.yml`, which would otherwise publish the Adminer database console on port 8080 to every computer in the office and switch on development mode. Check: `docker compose ps` must show only `db` and `backend`, and `http://<server-ip>:8080` must not open from another computer.
2. **The database port is closed to the network.** `compose.yml` publishes PostgreSQL only on `127.0.0.1`, so only the server computer itself can reach it. Check from another computer: connecting to `<server-ip>:5432` must fail.
3. **A sign-in lasts 8 hours** (`ACCESS_TOKEN_EXPIRE_MINUTES`, default 480), so a screen left open overnight or a copied token stops working the next day. People sign in once each morning. Before this change it was 8 days.
4. **No browser or proxy keeps API answers.** Every `/api/` response carries `Cache-Control: no-store`, so resident data is not stored in a browser cache on a shared computer. Resident photos already had `private, no-store`.
5. **Encrypted backups (patch 52).** Every backup file is locked with a public key, so a stolen backup file, a stolen external drive or a copied `backups\` folder cannot be read. The computer only holds the public key (`backups\backup-public.pem`), which can lock but not open. Opening needs the private key file (`backup-private.pem`) AND the passphrase.
   **Set it up once (administrator, before the first real backup):**
   1. Run `docker compose -f compose.yml exec backend python -m app.backup_cli make-key`. Type a passphrase of at least 16 characters twice (six unrelated words is good). It writes `backups\backup-public.pem` and `backups\backup-private.pem`. It never replaces an existing key.
   2. **Write the passphrase on paper, seal it and keep it somewhere safe. It cannot be recovered; without it every encrypted backup is lost.** Do not store it in `.env`, in a photo or in a file on this computer.
   3. Copy `backup-private.pem` to a USB drive kept away from this computer (a second copy in another place is wise), then delete it from `backups\`. Without the passphrase the file is useless to a thief, but a copy kept off the computer is the safe habit.
   4. Add `BACKUP_REQUIRE_ENCRYPTION=true` to `.env` (the line is in `.env.example`) and restart: `docker compose -f compose.yml up -d`. From now on a backup, and the safety copy made before a database update, is refused while there is no key, so a plain file can never appear by accident.
   5. Press **Back up now**. Pass: the new file is named `mayondon-db-….dump.enc`, no `.dump` file appeared next to it.
   **Prove it opens (do this now and again every few months):** `docker compose -f compose.yml run --rm -e MIGRATE_ON_START=false -v "<folder of the USB drive>:/keys:ro" backend python -m app.backup_cli decrypt --in /backups/<file>.dump.enc --key /keys/backup-private.pem --check` and type the passphrase. Pass: it says `OK: the passphrase and key open this backup`. A wrong passphrase must say `Wrong passphrase, or this is not the key file.`
   **Restore an encrypted backup:** the page shows `.\scripts\restore-db.ps1 -BackupFile .\backups\<file>.dump.enc -KeyFile <path to your private key file>`; replace the last part with the USB path, run it, type the passphrase from the sealed paper when asked and `RESTORE` to confirm. The plain copy exists in `backups\` only for the seconds it takes to copy it into the database container (BitLocker, below, protects that moment). A wrong passphrase changes nothing.
   **Notes.** *Verify file* on an encrypted backup checks the checksum and the file structure only; the real proof is the `--check` command above. `scripts\backup-db.ps1` refuses to run once the key exists (it would write a plain file) unless you add `-AllowPlain`. Old plain `mayondon-db-….dump` and `mayondon-premigrate-….dump` files made before the key existed stay readable by anyone: after the first encrypted backup is proven, delete them by hand (and from any external drive). Rotating the key later means making a new pair and keeping the old private key and passphrase for as long as old backups are kept.
6. **Reading and exporting resident data is logged (patch 53).** The Activity Log (System Administrator sees everyone's rows; staff see only their own) now has: `Resident record viewed` (`resident.view`, one row per person and resident per 10 minutes, no personal values), `Resident list viewed` (`resident.list`) and `Barangay ID list viewed` (`barangay_id.list`) when someone browses the whole list WITHOUT typing a name (a name search is a targeted lookup and is not logged; the row holds only the status filter and how many residents the list had), and `Report exported or printed` (`report.export`, module Reports, with the report, period and "CSV file" or "printed"). The Dashboard's recent-activity box hides the read rows so changes stay visible; the Activity Log page shows them (filter by action or module). A report export or print does not start if its row cannot be written. **Check:** open a resident profile, then Reports > Export CSV; as the administrator open Activity Log and see both rows. Opening the same profile again within 10 minutes adds no second row. Not logged on purpose: name searches, the photo itself (it opens with the profile), aggregate Dashboard numbers.
7. **HTTPS on the office network (patch 54; off until you switch it on).** Without it everything between a browser and the server, passwords and resident data included, crosses the office network readable by anyone plugged into it, and the camera for ID photos only works on the server computer itself (browsers need `localhost` or HTTPS). Patch 54 adds a small proxy (Caddy, container `caddy`, settings in `deploy/Caddyfile`) that makes its OWN certificate authority, so no internet and no outside service is used. **Applying the patch changes nothing by itself**; the proxy starts only after you do this once, on the server computer:
   1. Give the server computer a fixed address (router reservation or Windows setting) and note it, for example `192.168.1.10`. If it changes later the certificate no longer matches and step 3 is repeated.
   2. In `.env` uncomment and fill the four lines `COMPOSE_PROFILES=https`, `HTTPS_HOST=<that address>`, `APP_BIND=127.0.0.1`, `FORWARDED_ALLOW_IPS=*` (they are in `.env.example`). `APP_BIND` makes plain `http://<address>:8000` stop working from other computers; `http://localhost:8000` still works on the server computer. Then `docker compose -f compose.yml build backend` (first time only, for the app change) and `docker compose -f compose.yml up -d`. `docker compose -f compose.yml ps` must now show `db`, `backend` and `caddy`.
   3. Run `.\scripts\export-https-root.ps1`. It saves `mayondon-office-root.crt` (a PUBLIC certificate, safe on a USB drive) and prints its thumbprint.
   4. On EACH office computer, once: copy that file there and run `.\scripts\trust-office-https.ps1 -CertFile <path>` (or double-click the file, Install Certificate, Current User, "Trusted Root Certification Authorities"). Compare the thumbprint Windows shows with the one from step 3, answer Yes. Firefox only: `about:config`, set `security.enterprise_roots.enabled` to `true`.
   5. In Windows Defender Firewall (Private profile only) allow inbound TCP **443** and **80** and REMOVE the rule for 8000.
   **Checks:** (a) from another computer `https://<address>` opens the sign-in page with a padlock and no warning; (b) `http://<address>` jumps to `https://`; (c) `http://<address>:8000` no longer opens from another computer; (d) on that computer the camera in New Issuance works; (e) sign in, open Records, issue and print one document as usual; (f) restart the server computer and check (a) again. **If a browser still warns:** the certificate was not trusted on that computer (step 4) or you typed an address that is not `HTTPS_HOST`; use the exact address. **Keep safe:** the Docker volume `caddy-data` holds the authority's private key; if it is deleted (for example `docker compose down -v`, which you must never run) every computer must trust a new authority. The authority itself lasts about ten years; the proxy renews the short-lived server certificate by itself. Sign-ins and `Strict-Transport-Security` (30 days) then require HTTPS from browsers that have seen it; to go back to HTTP, comment the four lines, `up -d`, and wait out or clear the browsers' HSTS memory.
   **HTTPS by name instead of an address (tested on one computer, patch 54).** An address works, but a name survives a change of address, so the certificate never has to be trusted again. Use it when the router can give every computer the same name, or when you accept one line per computer.
   1. Choose a name that ends in `.test` (reserved for testing, never resolves on the internet), for example `brgy-mayondon.test`. Set `HTTPS_HOST=brgy-mayondon.test` in step 2 above instead of the address.
   2. Make every computer, including the server, resolve the name to the server's fixed address. Best: one entry in the router's local DNS (or DHCP host names) if it has one. Otherwise on each computer, as administrator, add the line `192.168.1.10 brgy-mayondon.test` (your server address) to `C:\Windows\System32\drivers\etc\hosts`. Check with `ping brgy-mayondon.test`: it must answer from the server address.
   3. Trust the root certificate on each computer exactly as in step 4 (Edge and Chrome use the Windows list; Firefox needs `security.enterprise_roots.enabled`). Then open `https://brgy-mayondon.test`.
   4. `curl` on Windows needs `--ssl-no-revoke` against this proxy (the local authority has no revocation service; the certificate chain is still checked). Browsers do not need it.
   5. `docker compose -f compose.yml ps` shows `adminer` and `mailpit` only on a computer that uses the development files; on the server always use `docker compose -f compose.yml ...` (item 1) and do not delete containers you have not identified.
   **Not yet tested:** a second computer on the office network and the install at the barangay; run checks (a) to (f) above there.
8. **BitLocker on the server computer's disk (patch 55; Windows setting, no code).** Everything on the server computer is stored readable on its disk: the database (inside Docker's data disk), `backups\`, `.env` with the secrets, and the photos. Someone who steals the computer, or only its disk, can read all of it from another machine without knowing any password. BitLocker encrypts the whole disk so that this fails. The encrypted backups of item 5 protect the backup files only; this protects the live data and the short moment a plain copy exists during a restore. Do this once, as a Windows administrator, **before real resident data goes in** (encrypting an empty disk takes minutes; the same step later takes longer but is safe).
   1. **Find out what you have.** Settings > System > About shows the Windows edition. *Windows Pro, Enterprise or Education:* use BitLocker (Control Panel > BitLocker Drive Encryption, or right-click the drive in File Explorer > Turn on BitLocker). *Windows Home:* BitLocker is not offered; use Settings > Privacy & security > Device encryption if it is listed (it needs a Microsoft account and a TPM); if neither exists, upgrade to Pro, which is the proper fix, and record the decision.
   2. **Which drives.** Encrypt the drive that holds the project folder (`backups\`, `.env`) AND the drive that holds Docker Desktop's data (by default `C:\Users\<name>\AppData\Local\Docker`, see Docker Desktop > Settings > Resources > Advanced > Disk image location). On most computers that is the same `C:` drive, so one drive is enough. If the project or Docker is on another drive, encrypt that drive too. Choose "Encrypt used disk space only" for a new computer and "Encrypt entire drive" for one that has been in use.
   3. **Save the recovery key away from the computer.** BitLocker shows a 48-digit recovery key; choose **Save to a file** or **Print** and put it on the same kind of USB drive or paper as the backup passphrase in item 5, in a different sealed envelope, held by the administrator. Do NOT save it on the encrypted drive and do not leave it only in a Microsoft account. Without it, a motherboard or firmware change, or a failed update, can lock everyone out of the data for good. It cannot be recovered later by anyone.
   4. **Start-up choice (decided for this office, owner may overrule).** The default, TPM only, unlocks the disk by itself at power-on and shows the normal Windows sign-in; it keeps the restart-and-recover behaviour of section B (the server comes back after a power cut with nobody typing a PIN) and protects against a stolen disk or a stolen computer that is switched off. It does NOT protect a stolen computer that is switched on and signed in, or one whose Windows password is guessed; so keep the Windows account on the server computer on a long password, never leave it signed in unattended and use the lock screen. A stronger option, a PIN at start-up (Local Group Policy > Computer Configuration > Administrative Templates > Windows Components > BitLocker Drive Encryption > Operating System Drives > "Require additional authentication at startup"), protects a stolen powered-off computer even from a thief who knows the Windows password, but then someone must type the PIN after every restart, so the system stays down after a power cut until a person arrives. Pick one and write it in the result sheet.
   5. **Wait for encryption to finish.** The computer can be used meanwhile; the Docker containers keep running. When BitLocker Drive Encryption shows the drive as "BitLocker on", restart the computer once and check the system comes back (section B).
   **Checks:** (a) in a PowerShell window opened as administrator run `manage-bde -status C:` (use each drive letter you chose). Pass: `Conversion Status: Fully Encrypted` (or `Used Space Only Encrypted`), `Percentage Encrypted: 100.0%`, `Protection Status: Protection On`, and a `Numerical Password` entry under Key Protectors. (b) The recovery key file or paper exists, is not on this computer, and one person other than the person who set it up knows where it is. (c) After a restart, `docker compose -f compose.yml ps` shows `db` and `backend` running (and `caddy` if item 7 is on) and the sign-in page loads, as in section B. (d) Press **Back up now** and run one restore of a TEST database as in item 5, to confirm nothing about disk encryption broke the backup folder or the Docker volumes. **Notes.** BitLocker does not replace the sign-in rules, the lockout, the audit log or the encrypted backups; it covers the one threat of the disk leaving the building. A copy of `backups\` on an external drive is already encrypted by item 5; BitLocker To Go on that drive is optional. Hibernation and the paging file sit on the encrypted drive and are covered. If Windows asks for the recovery key after an update or a hardware change, that is normal: type it once, then check that the drive still reads "Protection On".
9. **Automatic sign-out after 30 minutes of no activity (patch 56).** A screen left open on a shared computer no longer keeps resident records on view. After 30 minutes with no mouse, keyboard, touch or scroll activity the page shows "Are you still there?" with a one-minute countdown; **Stay signed in** (or Esc) carries on, **Sign out now** leaves at once, and with no answer the person is signed out and the sign-in page says why. Moving the mouse while the warning shows does not hide it, so a bumped desk cannot cancel it. Several tabs of the same browser share the clock, so working in one keeps the others open and they all sign out together. The check compares clock times every second, so a computer that went to sleep signs out as soon as it wakes. **Check:** sign in, leave the screen alone for 29 minutes, see the warning at about 29 minutes 30 seconds, press **Stay signed in**, and confirm the page keeps working; leave it again for 31 minutes and confirm the sign-in page appears with the notice. **Limits to know:** it is a browser-side convenience, not a cancelled sign-in; the token itself still ends after 8 hours (item 3), so a copied token works until then. Unsaved typing counts as activity, but a form left untouched for 30 minutes is lost (an issuance draft already saved on the server is kept). To change the 30 minutes, edit `IDLE_MINUTES` in `frontend/src/hooks/useIdleSignOut.ts` and rebuild the backend image (the screens are built into it).
10. **Old "viewed" rows can expire (patch 57; nothing is deleted unless you run the command).** Patch 53 made the Activity Log record every profile opened and every whole list browsed, so it grows quickly. Rows that record a change, a sign-in, a print, an export or anything else are kept for ever. Only the three READ kinds (`resident.view`, `resident.list`, `barangay_id.list`) can expire, and the database itself refuses to delete any other row, any READ row younger than 90 days, or the whole table (this narrows the old rule "audit_log is append only" in `docs/10` decision 24 to one exception; the owner may overrule it by asking for the old trigger back). **Count first:** `docker compose -f compose.yml exec backend python -m app.audit_cli prune-reads` prints how many "viewed" rows are older than 365 days and deletes nothing. **Delete:** add `--delete`; one row "Old viewed entries removed" (module Activity Log, with the count and the days kept) is written so the clean-up is itself on record. `--keep-days N` changes the 365 (not below 90). Run it by hand when you wish, for example once a year; it is not scheduled. Take a backup first (item 5). **Check:** after a `--delete` open Activity Log as the administrator and find the "Old viewed entries removed" row; the older "viewed" rows are gone and every other row is still there. The database change needs the backend image rebuilt and restarted (`docker compose -f compose.yml build backend` then `up -d`; the start-up saves a safety copy of the database first).
11. **Replacing the secrets (patch 62; nothing changes until you run `apply`).** `SECRET_KEY` (signs every sign-in), the database password and the administrator password were set up during development. Replace them once the masterlist import is checked and before real use. The tool is `backend/app/rotate_secrets_cli.py`; it **never prints a secret**, and it has been tested only on a throw-away database role, not on this system.
   **What changes.** (1) `SECRET_KEY` in `.env` becomes a new random value: everyone is signed out once and any unused password-reset link stops working. (2) `POSTGRES_PASSWORD` in `.env` (and the password inside `DATABASE_URL` if `.env` has that line) becomes a new random value, and the same change is made inside the running database (`ALTER ROLE`); the tool proves the new password works and the old one no longer does BEFORE it touches `.env`. (3) The administrator types a new password (12 characters or more; not shown, not saved anywhere); `FIRST_SUPERUSER_PASSWORD` in `.env` becomes a random value that belongs to no account. (4) The Activity Log gets two rows: `Password changed` for the administrator and `System secrets changed` (names only). **What does not change:** backup keys and files, residents, issuances, other accounts' passwords (`FIRST_STAFF_PASSWORD` too), HTTPS certificates.
   **Before you start.** Make an encrypted backup with **Back up now** (the tool refuses to start without a backup from the last 2 hours, and without an encrypted one when encryption is set up) and prove it opens (item 5). Choose the administrator's new password and keep it where the passphrase is kept. Do it when nobody is working.
   **Steps (PowerShell in the project folder).**
   1. Dry run, changes nothing: `docker compose -f compose.yml run --rm -v "${PWD}:/work" backend python -m app.rotate_secrets_cli plan`. Read the list. Pass: it ends with `Checks passed`. If it says `It would NOT start yet`, fix what it names (a stale backup, or `.env` and the running database disagreeing: run `docker compose -f compose.yml up -d` first).
   2. Do it: `docker compose -f compose.yml run --rm -v "${PWD}:/work" backend python -m app.rotate_secrets_cli apply --confirm ROTATE`, then type the new administrator password twice. It saves the old file as `.env.before-rotation-<time>` beside `.env`.
   3. Restart so the backend reads the new `.env`: `docker compose -f compose.yml up -d --force-recreate` (the database restarts for a few seconds; its data stays).
   4. Sign in as the administrator with the NEW password. Open Activity Log: the two new rows are there. Make a new encrypted backup.
   5. Move `.env.before-rotation-<time>` to the USB drive of item 5 (it holds the OLD secrets) and delete it from the computer once you are sure all is well. Do not email it or put it in the repository (`.env.*` is ignored by Git).
   **If something goes wrong.** If `apply` itself reports a failure it has already put the old database password back and left `.env` as it was; read its message. If it reports that the old password could NOT be put back, run the rollback below at once. To undo a finished rotation: `docker compose -f compose.yml run --rm -v "${PWD}:/work" backend python -m app.rotate_secrets_cli rollback --old-env /work/.env.before-rotation-<time> --confirm ROLLBACK`, then `docker compose -f compose.yml up -d --force-recreate`. Rollback puts the old `.env` and the old database password back; it does **not** undo the administrator's new password (that is yours; change it in the app if needed). If the backend will not start after a restart: `docker compose -f compose.yml logs backend`; a database login error means `.env` and the database disagree, so run the rollback. As a last resort restore the backup from step 4's predecessor (item 5).
   **Notes.** The new database password is visible to Postgres during the change; the default Postgres setting does not write it to a log. Adminer, if you use the development files on another computer, needs the new password too. A person's own sign-in password is never touched except the administrator's.
